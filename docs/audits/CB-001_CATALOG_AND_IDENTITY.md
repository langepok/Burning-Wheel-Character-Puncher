# CB-001 — Catalog Identity and Requirement Audit

Status: **Audit supplement for Issue #1**

Purpose: capture data-model findings discovered while visually checking the Human lifepath tables for the first supported slice. This document intentionally records implementation facts and concise paraphrases rather than reproducing the rulebook tables.

Source ranges checked against rendered PDF pages:

- Peasant Setting: PDF pp. 165–166 (printed pp. 163–164)
- Villager Setting: PDF pp. 167–171 (printed pp. 165–169)
- City Dweller Setting: PDF pp. 172–179 (printed pp. 170–177)
- Professional Soldier Subsetting: PDF pp. 189–191 (printed pp. 187–189)
- Repeating Lifepaths / Law of Diminishing Returns: PDF p. 86

## 1. Current slice is not a small catalog

A visual row count gives the following first-slice catalog size:

| Area | Printed lifepath variants |
| --- | ---: |
| Peasant | 19 |
| Villager | 41 |
| City Dweller | 70 |
| Professional Soldier | 21 |
| **Total** | **151** |

These are printed **row variants**, not necessarily 151 independent conceptual lifepath identities. Several names recur in multiple settings with different grants, Leads or skill lists.

This is large enough that production data transcription should be treated as its own audited task rather than casually copied from OCR inside an engine PR.

## 2. A printed row needs an identity distinct from the conceptual lifepath family

### RAW evidence

The Law of Diminishing Returns says its repeat rules still apply if a character moves to another setting and finds the **same lifepath** there (Character Burner, PDF p. 86).

The supported Human tables contain many same-named rows in different settings. Examples include:

- Runner;
- Conscript;
- Groom;
- Sailor;
- Laborer;
- Taskmaster;
- Clerk;
- Shopkeeper;
- Apprentice;
- Journeyman;
- Armorer;
- Master Craftsman;
- Merchant.

Some same-named variants have meaningfully different row data. Therefore a single id cannot safely serve both “this exact printed row” and “the repeated lifepath concept used by cross-setting repeat logic.”

### Recommended data model

Use two identities:

```ts
type LifepathVariantId = string; // exact setting/table row
type LifepathFamilyId = string;  // conceptual same-lifepath identity

interface LifepathRecord {
  id: LifepathVariantId;
  familyId: LifepathFamilyId;
  settingId: SettingId;
  name: string;
  // row-specific data follows
}
```

Example shape only:

```ts
{
  id: 'human.villager.apprentice',
  familyId: 'human.apprentice',
  settingId: 'human.villager',
  name: 'Apprentice'
}
```

The exact family mapping must be audited during catalog transcription rather than generated by fuzzy name matching at runtime.

### Consequences

- repeat occurrence count should be able to operate on `familyId`;
- the currently selected row still keeps its own row-specific years, resources, stat grant, Leads and lists;
- history stores `id`, not only `familyId`, so undo and grants remain exact;
- tests must include a repeated lifepath reached through a different setting.

### OPEN — unqualified named prerequisites

Requirements often say simply `Apprentice`, `Journeyman`, `Student`, etc., even though same-named variants can exist in more than one setting.

The schema should therefore support both:

```ts
{ kind: 'priorVariant'; ids: LifepathVariantId[] }
{ kind: 'priorFamily'; familyIds: LifepathFamilyId[] }
```

Do **not** force all named prerequisites to exact row ids until the data audit establishes whether the printed wording intends the conceptual family. This distinction can materially change legal builds.

## 3. Canonical setting ids and table aliases

The printed tables use shortened names. The data layer should normalize them before rules evaluation.

Recommended canonical ids for all destinations encountered by the supported slice:

| Printed label/abbreviation | Canonical id |
| --- | --- |
| Peasant | `human.peasant` |
| Village / Villager | `human.villager` |
| City / City Dweller | `human.city-dweller` |
| Soldier | `human.professional-soldier` |
| Serv. / Servitude | `human.servitude-captive` |
| Sea / Seafaring | `human.seafaring` |
| Religious | `human.religious` |
| Outcast | `human.outcast` |
| Noble | `human.noble` |
| Court / Noble Court | `human.noble-court` |

This normalization is implementation/data plumbing; it does not change RAW.

## 4. Requirement algebra needs several additional predicate types

The visual catalog pass confirms the earlier requirement algebra and exposes additional cases that should be explicit rather than hidden in custom callbacks.

Recommended capabilities:

```ts
type Requirement =
  | { kind: 'allOf'; items: Requirement[] }
  | { kind: 'anyOf'; items: Requirement[] }
  | { kind: 'priorVariant'; ids: LifepathVariantId[]; minCount?: number }
  | { kind: 'priorFamily'; familyIds: LifepathFamilyId[]; minCount?: number }
  | { kind: 'priorSetting'; settingIds: SettingId[]; minCount?: number }
  | { kind: 'priorTag'; tag: LifepathTag; minCount?: number }
  | { kind: 'priorLifepathContainsSkill'; skillId: SkillId }
  | { kind: 'hasTrait'; traitId: TraitId }
  | { kind: 'characterGender'; value: 'female' | 'male' }
  | { kind: 'position'; allowed?: number[]; disallowed?: number[] }
  | { kind: 'maxOccurrences'; value: number }
  | { kind: 'startingAge'; minExclusive?: number; minInclusive?: number }
  | { kind: 'maxTotalLifepaths'; value: number }
  | { kind: 'custom'; ruleId: string };
```

Important additions from this pass:

- `hasTrait`: City Bishop can be enabled by the **Your Grace** trait as one branch of its requirement;
- `priorFamily`: needed to avoid prematurely treating every unqualified repeated name as a setting-local row;
- `characterGender` is distinct from `priorTag('female-gender-specific')`: Human Midwife can be enabled by a prior female gender-specific lifepath, while other rows directly restrict the character to female.

## 5. Semantic categories found in or required by the supported slice

Some categories are not setting membership and cannot safely be inferred from strings at runtime.

The first-slice rules reference at least:

- `guard` — e.g. Duelist / Sergeant-at-Arms requirements;
- `sergeant` — Guard Captain accepts “any sergeant”;
- `priest` — Professional Soldier Chaplain accepts any priest lifepath;
- `acolyte` — Itinerant Priest accepts any Acolyte LP from any setting;
- `sorcerous` — Villager Scholar accepts any sorcerous lifepath;
- `horse-related` — Professional Soldier Cavalryman asks for a prior lifepath having to do with horses;
- `female-gender-specific` — Peasant Midwife references a prior female gender-specific lifepath.

Use curated tags or equivalent explicit metadata. Do not qualify a path merely because its English name contains `Guard`, `Priest`, `Horse`, etc.

A separate catalog audit must record membership for each semantic category actually needed by production data.

## 6. “Any X lifepath” is not always a semantic tag

Some category-looking requirements are simply setting/subsetting membership.

Examples:

- `any Soldier lifepath` → canonical Professional Soldier setting membership;
- `any Professional Soldier lifepath` → Professional Soldier setting membership;
- `any Religious setting lifepath` → Religious subsetting membership;
- `any Noble, Noble Court or Religious lifepath` → membership in one of those listed areas;
- `any Outcast or Soldier lifepath` → membership in the listed areas.

Prefer `priorSetting` for these. Reserve tags for categories that genuinely cut across settings or cannot be represented by setting identity.

## 7. Leads are predicates, not only destination arrays

The visual pass confirms Lead forms including:

- fixed destination lists;
- `Any`;
- `Any except Noble`;
- `Any except Noble and Court`.

The earlier `LeadRule` algebra remains appropriate:

```ts
type LeadRule =
  | { kind: 'to'; settingIds: SettingId[] }
  | { kind: 'any' }
  | { kind: 'anyExcept'; excludedSettingIds: SettingId[] };
```

A parser/importer must treat punctuation such as comma/semicolon as presentation, not as a second rules concept, unless a future source establishes otherwise.

## 8. Row data has more shapes than scalar grants

### Mixed skill-point pools

Rows can grant ordinary lifepath skill points and General points simultaneously. Store these separately.

```ts
skillPoints: {
  lifepath: number;
  general: number;
}
```

### Resource formulas / special effects

Country Wife, Village Wife and City Wife use a `5+` style resource entry tied to a husband's selected lifepath. Keep an explicit named special rule; do not flatten the value to 5.

### Stat grants

Keep the existing distinction:

- `+M`;
- `+P`;
- `+M/P` (choose one pool);
- `+M, P` (grant both).

### Zero trait points vs discretionary trait points

Do not conflate:

- `Traits: —` / no points;
- `Traits: 1 pt: —` / one discretionary point with no required listed trait.

This distinction affects point totals and validation.

## 9. Skill list entries can themselves be structured choices

The supported tables already contain entries that are not just fixed skill ids, for example:

- `Javelin or Bow`;
- `any “smith” skill`;
- `Appropriate Weapons`;
- training skills marked by the training symbol.

Therefore the eventual skill-list data model should support at least fixed skills, one-of choices and named choice rules. Do not encode `Javelin or Bow` as a single fake skill string.

A possible shape:

```ts
type LifepathSkillEntry =
  | { kind: 'skill'; skillId: SkillId }
  | { kind: 'oneOf'; skillIds: SkillId[] }
  | { kind: 'choiceRule'; ruleId: string };
```

Training/special opening cost belongs in skill metadata or an explicit entry modifier, not in React.

## 11. Regression tests implied by this audit

Add to the M1/M2 data/rules test plan:

1. two variants with the same family id remain distinct catalog rows;
2. repeat count can follow the family across a setting transition;
3. undo restores the exact chosen variant and its grants;
4. setting-backed requirement uses canonical setting membership, not a semantic tag;
5. semantic tag requirement uses curated metadata, not string matching;
6. a trait-based requirement can be expressed without a custom callback;
7. `Traits: —` and `1 pt: —` produce different point grants;
8. mixed ordinary/General skill grants stay in distinct pools;
9. a structured skill choice is not represented as a fake skill id;
10. wife-path `5+` resources are not silently truncated to a scalar 5.

## 12. Recommended next task split

Issue #1 can define rules/schema/acceptance criteria, but the 151-row catalog should be transcribed and validated in a dedicated data task before claiming full first-slice content support.

That data task should:

- enter records in small batches by setting;
- visually verify every row against the rendered source;
- validate ids, family ids, years, resources, stat grants, Leads, point pools, restrictions and requirements;
- add catalog integrity tests;
- separately flag skill/trait metadata that belongs to later milestones;
- never import OCR output directly into production without visual review.
