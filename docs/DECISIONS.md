# Decisions

Durable project decisions live here. Rules-as-written belong in `RULES_NOTES.md`; this file is for implementation, architecture, interpretation and UX choices.

## D-001 — Clean-room Character Burner v2

**Status:** Accepted

The new application is implemented from scratch. The previous single-file HTML prototype is not migrated and is not a rules source. It may be consulted only as historical UX reference.

**Reason:** The prototype mixed rules logic, state and presentation, making localized fixes prone to regressions.

## D-002 — Rules logic is separate from UI

**Status:** Accepted

Rules evaluation and calculations must be framework-independent. React components consume rule results; they do not determine legality themselves.

## D-003 — Character Burner is data-driven

**Status:** Accepted

Lifepaths, settings, Leads, requirements, restrictions and point grants are represented declaratively wherever practical. Special cases should be explicit and testable rather than hidden in component conditionals.

## D-004 — Current temporary human scope is Peasant + Villager + City + Professional Soldier

**Status:** Accepted — temporary scope

The first playable human slice exposes **Born Peasant**, **Village Born** and **City Born** as initial choices.

The supported lifepath area for this slice includes the **Peasant Setting**, **Villager Setting**, **City Dweller Setting** and **Professional Soldier Subsetting**, including legal transitions among them where supported by Leads and requirements.

Professional Soldier is included as a supported reachable area; this is not a claim that it has its own Born lifepath. Likewise, this temporary scope is a product decision, not a claim that these are the only legal human Born lifepaths or settings in Burning Wheel.

This decision expires when the full human lifepath data audit is implemented.

## D-005 — Exact point accounting is an invariant

**Status:** Accepted

Every character-burning purchase records enough provenance to undo exactly what was spent. Reset/rollback must conserve point pools and must not infer refunds solely from the current exponent.

## D-006 — Skill adjustment UI uses +1 / -1

**Status:** Accepted

Opened skills display their exponent prominently and expose clear `+1` and `-1` controls. The rules layer remains responsible for determining whether either action is legal and what it costs/refunds.

## D-007 — Current web stack

**Status:** Accepted for v2 bootstrap

Use **TypeScript + React + Vite + Vitest** for the first implementation.

This is an engineering choice, not a Burning Wheel rule. Revisit only if the stack materially impedes rules accuracy, testing or maintainability.

## D-008 — Rulebook PDF stays outside Git

**Status:** Accepted

The legally obtained Burning Wheel reference PDF remains in the private ChatGPT Project used for rule research. The public repository stores concise paraphrases, source references and implementation data, not the PDF or large verbatim excerpts.

## D-009 — Rule explanations are part of the product

**Status:** Accepted

The simulator is a training tool, not merely a form. When practical, disabled or rejected actions should expose a reason generated by the rules layer and rendered as a clear explanation in the UI.

## D-010 — Interpretation policy for small RAW gaps

**Status:** Accepted

Burning Wheel sometimes relies on context and ordinary common sense instead of spelling out every implication as a separate prohibition or exception. When the rulebook does not state a minor implication literally, the project may adopt a narrow interpretation if the surrounding rules, terminology and fictional meaning make the intended behavior clear.

Such a conclusion must be labeled **project interpretation**, not RAW. The implementation and tests should encode the interpretation explicitly so it can be revised without pretending the book said something it did not say.

If two materially different readings remain plausible, or the choice would significantly change legal builds or outcomes, the question remains **OPEN** until explicitly resolved. “Common sense” is not permission to silently invent convenience rules.

## D-011 — A character has exactly one Born lifepath

**Status:** Accepted — project interpretation

A character has exactly one Born lifepath, and it is always lifepath index 0. No Born lifepath may become legal again later through a Lead, setting transition or repeated-lifepath logic.

The rulebook explicitly requires the first lifepath to be Born and describes that path as the character's birth/childhood and starting setting. The audited passage does not separately contain a universal sentence saying that a Born path can never be selected later, so this is recorded under D-010 as an explicit interpretation rather than overstated as a literal RAW sentence.

Recommended rules-engine rejection reason: `BORN_LIFEPATH_NOT_FIRST`.

## D-012 — Final-age requirements stay lightweight in the UI

**Status:** Accepted — UX/implementation decision

Rare requirements phrased in terms of the character's final/starting age, such as Human Elder, do not justify a special intermediate legality state in the first implementation.

The product should:

- show the age requirement clearly in the lifepath description;
- allow the builder to remain simple rather than introducing a dedicated `LEGAL_WITH_PENDING_REQUIREMENT` status solely for this niche case;
- verify the requirement when final build validity is checked.

This decision is about product complexity and presentation. It does not change the wording of the underlying rule.

## D-013 — Round halved repeated-lifepath grants up

**Status:** Accepted — project interpretation

When the Law of Diminishing Returns grants **half** of a point pool from a repeated lifepath and the original value is odd, round the halved result **up**.

Examples:

- 5 skill points → 3;
- 7 resource points → 4.

The audited Law of Diminishing Returns states that these grants are halved but does not specify a rounding direction. This project intentionally chooses round-up as a favorable, simple interpretation for an already inefficient character-building choice. This must be labeled as a project interpretation, not RAW.

Implementation should use an explicit helper/test for this rule rather than relying on incidental JavaScript rounding behavior.

## D-014 — Duplicate lifepath names are qualified by setting in the UI

**Status:** Accepted — UX decision

When the same printed lifepath name exists in more than one setting/subsetting, the application presents a setting-qualified label so users can distinguish the variants at a glance.

Examples:

- `Peasant Conscript` vs `Villager Conscript`;
- `Villager Apprentice` vs `City Apprentice` where those variants exist;
- equivalent qualification for duplicate Runner, Sailor, Journeyman, Armorer and other repeated names.

This is a presentation decision, not a rules change. Production data must preserve the exact printed/source name separately from its UI label. `variantId`, `familyId`, setting identity and rules behavior must never be derived from the decorated display string.

Preferred implementation: keep `sourceName` (or equivalent) canonical and derive a display label from setting metadata plus the source name whenever a collision exists. A setting may expose a concise UI qualifier such as `Peasant`, `Villager`, `City` or `Soldier` without changing its canonical setting id/name.

## D-015 — Core architecture must support additional stocks and settings without redesign

**Status:** Accepted — architecture decision

The Human first slice is implementation order, not an architectural boundary. Core catalog, rules and character-state abstractions must be capable of loading additional stocks/settings (for example Dwarves, Orcs and later supported Burning Wheel stocks) without rewriting the generic engine or React application structure.

Consequences:

- generic domain code must not assume `human` or hard-code the four temporary Human settings;
- stock, setting/subsetting and lifepath identities are explicit data, not TypeScript branches scattered through the UI;
- the rules engine consumes catalogs/registries through generic interfaces;
- stock-specific or setting-specific exceptions are represented as explicit data/predicate/special-rule capabilities rather than hidden Human-specific conditionals;
- adding a new supported stock should primarily mean adding validated content plus narrowly scoped rules extensions, not refactoring existing Human logic;
- tests should protect this boundary as the project grows.

The current implementation does **not** need a plugin framework or general-purpose rules DSL yet. We only preserve clean extension points so later content does not force a rewrite.

## D-016 — In-app custom content authoring is a long-term final milestone

**Status:** Accepted — product direction, deferred

In the long term, the application should be able to define/import/export custom stocks, settings and lifepaths through the application itself, rather than requiring source-code edits for every content pack.

This is deliberately deferred until the core Character Burner, equipment and training simulators are stable. Near-term implementation must not build an editor prematurely.

However, data formats introduced now should avoid needless obstacles to that future goal: prefer serializable, validated, versionable declarative content records with stable ids over code-only structures where practical.

A future authoring system should be able to reuse the same validation/catalog pipeline as built-in content rather than creating a second rules path.

## D-017 — Broad semantic lifepath categories are inclusive, explicit tags

**Status:** Accepted — project interpretation / data-curation policy

When RAW uses a broad fictional category such as `any guard lifepath`, `any Acolyte LP` or `a prior lifepath having to do with horses`, the project should model that category by explicit curated semantic tags.

The simulator must **not** add a second hidden “does this biography feel plausible?” gate after category membership is satisfied. Burning Wheel already permits unusual life histories; if a path genuinely belongs to the category, it qualifies and the player may explain the transition in the fiction.

Accepted current-slice interpretations include:

- Villager `Failed Acolyte` counts as `acolyte`;
- City Dweller `Guard Captain` counts as `guard`;
- plainly horse-focused current-slice paths are tagged `horse-related`, including both Groom variants, Farrier, Saddler and Cavalryman.

This does not authorize fuzzy runtime inference. Membership is recorded explicitly in audited data. Similar-looking or merely adjacent paths are not auto-tagged by substrings, skill names or UI labels.

## D-018 — Free Creation mode bypasses rules enforcement without rewriting RAW

**Status:** Accepted — product/architecture decision

The application will provide a **Free Creation** (sandbox) mode in addition to normal rules-enforced character burning.

In normal mode, RAW plus accepted project interpretations determine which actions are legal and point/requirement limits are enforced.

In Free Creation mode, those restrictions do not block the user's choices. As relevant subsystems are implemented, the user may deliberately create otherwise-illegal builds, including examples such as:

- multiple Born lifepaths or Born lifepaths in later positions;
- lifepaths without legal Leads/current-setting access;
- unmet lifepath requirements/restrictions;
- arbitrary repeated lifepaths;
- skills/traits chosen without the normal lifepath eligibility gates;
- stat, skill, trait and resource allocations beyond normal Burning Wheel limits where the corresponding editor supports direct adjustment.

Free Creation does **not** change RAW, mutate canonical content data or make an illegal build “rules-valid.” The same rule evaluators should remain available so the UI can optionally show warnings/explanations while the command policy allows the action.

Preferred architecture is an explicit enforcement policy such as `rules` vs `free`, not a second forked Character Burner engine. Save/load state should record the chosen mode so a sandbox build is never silently treated as rules-legal.

The near-term Free Creation mode operates on content available in the loaded catalog. Truly user-authored stocks/lifepaths/skills belong to the later D-016 content-authoring milestone and should then flow through the same sandbox mode.

## D-019 — Catalog foundation and explicit unresolved grant metadata

**Status:** Accepted — implementation decision for Issue #9

Content packs register stocks, settings, families, skill references and lifepath
variants through one stock-independent typed catalog API. Registration validates
ids and references; it does not evaluate character legality. Referenced families
and settings outside the loaded slice are explicitly reference-only definitions,
not fabricated lifepath rows. Incomplete skill-list metadata is marked partial.

Wife-derived skill-point scope is a three-way value: `ordinary-only`,
`ordinary-and-general`, or `unspecified`. Per the
[Issue #9 resolution](https://github.com/langepok/Burning-Wheel-Character-Puncher/issues/9#issuecomment-5994214609),
Country Wife uses `unspecified`, and Village Wife uses `ordinary-and-general`.
Unspecified is not false or ordinary-only. Later skill-allocation work must
resolve or surface it before applying the grant. This preserves a source gap;
it does not establish a new Burning Wheel rule.

Skill and resource fractions share an exact serializable numerator/denominator
type and validation. This representation implies no resource-rounding policy.

## D-020 — Data-driven Skill Catalog, schema before full transcription

**Status:** Accepted — architecture/scope decision for the Skill Catalog foundation

The full General Skill Catalog will be declarative content. The foundation uses
the verified [Issue #20 audit packet](https://github.com/langepok/Burning-Wheel-Character-Puncher/issues/20)
and representative examples from the task brief to prove the schema. Full A–Z
transcription belongs in a subsequent PR.

Complete `SkillDefinition` records and explicitly partial `SkillAuditFixture`
records have different coverage discriminants. Omitted fixture metadata means
untranscribed, not unrestricted or ordinary. Name-only references are not skill
definitions. Fixtures do not replace the current lifepath catalog's skill references.

## D-021 — FoRK guidance and contributor provenance

**Status:** Accepted — architecture decision implementing verified RAW

Printed FoRK suggestions are guidance, not an exhaustive whitelist. Concrete
skills, types, categories, Wise topics and contexts have structured representation.
Future adjudication must allow contextual contributors beyond the printed list.

Contributors preserve their source skill, evidence and ordinary/special behavior
identity. Astrology and Rune Casting reference a shared special FoRK descriptor;
flattening this to a dice count would lose reroll/subtraction behavior. This PR
does not implement a roll builder or dice evaluator.

## D-022 — Skill families and choices have separate identities

**Status:** Accepted — data modeling decision implementing verified RAW

Wises and History are families with separately owned topics and shared metadata
defaults. Named topics may override those defaults. Family/topic ids form a stable
pair, independent of display text. A family does not own one shared exponent.

Appropriate Weapons is a choice expression selecting real skills in context;
it is never registered as an owned skill. Broader families such as languages
and musical instruments await their own audits.

## D-023 — Skill definitions describe facts; integrations own subsystem behavior

**Status:** Accepted — architecture and repository-content decision

`SkillDefinition` metadata separates availability, opening and use requirements;
Training from Skill Type; printed markers from roll behavior; and semantic
relations from source aliases. Integration tags are indexes, not execution
permissions. Separate `SkillIntegration` records reserve a place for subsystem
links; Fight, Range and Cover, Resources, Injury and magic execution remains
outside the catalog.

Public data holds project-authored summaries and source references. Optional
future licensed full text must remain separate from public core data and must
never become runtime-parsed rules. Unresolved source references retain their
printed labels and tentative targets without silently resolving them.

The confirmed Antiphon audit keeps its direct tools as none. Its cross-reference
to the preceding skill-song creation stage belongs in structured magic-integration
metadata, not in ToolRequirement. Creation follows the chosen song's own rules
and tools; this does not propagate them to the later enchantment stage. No
inheritance evaluator or magic engine is introduced.

## D-024 — Composable audited skill metadata without identity normalization

**Status:** Accepted — schema-hardening decision for PR #21

The user's subsequent BWGR review corrects the initial Boxing/Martial Arts
interpretation: they are distinct skill identities with reusable mechanics,
not aliases. Preserve the printed Boxing heading and link Martial Arts with
a mechanics relation. No duplicated combat implementation follows from this.

Keep canonical Skill Type source labels, including Seafaring versus Seafarer.
Small boolean composition nodes describe tools, FoRK targets and target/activity
contexts; they are data, not a scripting language or evaluator. FoRK categories
use curated metadata, never substring matching. General literacy does not require
a cultural context. Non-Training base opening overrides need explicit provenance
and cannot replace Training costs; marker/type inference and Gray-opening metadata
are excluded. See the [review evidence](audits/SKILL_SCHEMA_FOUNDATION.md#pr-21-raw-review-corrections).

The subsequent PDF audit and user resolution extend tool composition with a
conditional context and then/otherwise branches. Dwarven Rune Script and Elven
Script require expendable tools for writing, not reading. Reuse activity nodes
and recursive tool validation; do not introduce a Script-specific node or an
evaluator. See [the A–Z audit](audits/GENERAL_SKILL_CATALOG_AZ.md).

The confirmed Blacksmith audit adds optional context to Resources interactions
and a generic circumstance-id leaf to SkillContext. The suitable-workplace
condition is independent of Workshop tools and is never inferred for other
skills. This extends descriptive metadata only; no Resources evaluator follows.

## D-025 — Created-object/result metadata belongs to equipment integration

**Status:** Accepted — A–Z source audit and explicit user resolution

Direct character Resources effects (tax recovery and cash generation) remain
ResourceInteraction. Valuation of a crafting result belongs to equipment/Resources
integration metadata. Store a created-item target, typed measure and integer delta;
Resources obstacle and Resources value dice are distinct measures. An optional
valuation tradeoff stores its pre-roll choice and crafting-obstacle cost separately
from the automatic modifier. Do not infer repeatability or evaluate prices,
crafting tests, equipment or character Resources.

Gem Artifice and Gemcraft (BWGR 275 / PDF 277), with the White Metal Artifice
representative (308/310), motivate this contract. Magic matrix/Antiphon references
are independent of valuation. Other equipment properties (tool bonuses, weapon
statistics, quality) are not valuation and must not be forced into its measures.
Partial representatives do not replace the complete A–Z production transcription.

The confirmed Forge Artifice audit (274/276) extends this boundary with a separate
EquipmentUseEffect. It stores the created equipment kind, advantage dice for its
user, optional crafting-obstacle cost, explicit repeatability and successful final
creation condition. Forge's cost/bonus is per increment; Black Metal Artifice
(260/262) leaves repeatability unspecified. Unspecified is not a boolean permission
or prohibition. A single-tradeoff value is available for sources that establish it.
Do not add a maximum, evaluate stacking or convert use bonuses into skill bonuses
or Resources value. Descriptor validation is content integrity, not rules execution.

The confirmed Siege Engineer audit (296/298) adds CreatedEquipmentCapability:
completed war machines count as tools for destroying structures. A purpose-scoped
capability of crafted equipment is independent of construction ToolRequirement,
numeric use bonuses and structure resistance. Do not infer operating abilities,
damage or destruction execution from this role. This extends the same boundary.

The confirmed Hallmaster (276/278) and Stone Artifice (301/303) audit extends
created-object/result metadata to structures. A distinct StructureResistance
stores the created structure, optional building-obstacle cost and the obstacle
penalty on tests against that structure for alteration/destruction. Both sources
leave repeatability unspecified. This is neither a use bonus to the equipment
user nor Resources valuation. No HP, durability, stacking or destruction engine
follows from this descriptor; the equipment integration boundary is unchanged.

The confirmed Leathercraft (280/282) audit extends result acquisition with
EquipmentResult: a named equipment target, an allOf enchantment combination
and a skill-specific use effect. Training components resolve as Training;
spell-song source names remain external magic references, not General skills.
This does not duplicate the existing generic Antiphon/matrix cross-reference:
it records the particular combination and resulting benefit. No crafting cost,
tool inheritance or enchanting/equipment-use execution is implied. The belt
example supplies no numeric effect and remains a source-backed magic summary.

The confirmed Nogger audit (285–286 / 287–288) extends this boundary with
CraftedConsumableEffect: results triggered by consuming the crafted product,
not by its crafting test. Cases have source-authored recipient stock/not-stock
conditions and dose/threshold metadata. Next-ability and scene skill-type scopes
are separate. Explicit once-active/non-stacking does not imply per-dose repetition;
other repetition remains unspecified. Cases are independent conditions, not XOR.
A limited attribute-derived duration stores hour unit, base and subtracted current
attribute exponent, never an arbitrary formula or a computed/clamped result.
Unspecified duration/restorative denial is explicit where supported. No stock
engine assumptions, inventory consumption, scene clock, drinking, intoxication,
Health/Forte or duration evaluator follows. Consumable results are distinct from
valuation, tool-use bonuses and skill-test outcomes.

The confirmed Poisons audit (288–289 / 290–291) extends this boundary with
CraftedPoison: independent potency and intended-delivery dimensions for a created
product. Potency stores base crafting obstacle plus obstacle penalty or fixed
wound shade/exponent; delivery stores its own crafting-obstacle delta. Penalty
scope is source-unspecified, not all-tests. No duration, onset, resistance,
recovery or repeated-exposure semantics are inferred. B10 wound is not created
device Mark, damage dice or weapon damage. Composition totals belong to tests;
no arithmetic, exposure or wound processing follows from descriptor validation.
The equipment integration is indexed for the poisons subsystem separately from
Nogger consumption and skill-test outcome metadata.

The confirmed Vile Poisoner audit (306/308) adds a mutually exclusive product-level
CraftedPoison form rather than forcing distinct products into independent potency/
delivery combinations. Each product retains source exposure, optional resistance
and outcomes. Source-shaped physical/martial/social scopes are not inferred lists
of stats or Skill Types. A shared resistance-test margin-of-failure reference feeds
permanent Health/Health-maximum reductions. Literal Mark injection and a named
six-plus-victim-Forte exchange delay preserve the additional wound without hit,
Health or timer execution. No dose, coating persistence, stacking, recovery or
arbitrary formula semantics are inferred. These remain crafted-output facts.

The confirmed War Art audit (307/309) adds equipment-result metadata for independent
physical-weapon improvement options, source-specific armor/shield qualities and
effective crafting-skill shade eligibility. Named current-weapon VA/Power obstacle
references are distinct from a fixed crafting-obstacle adjustment; Balance Dice
remain an external equipment capability. Accepted interpretation: each distinct
improvement may occur once per physical weapon, without a choose-one restriction.
War Art's armor-quality rerolls retain source-specific provenance and an unresolved
source-conflict marker for the later Equipment audit, without normalization or a
stacking/exclusivity policy. Gray-device eligibility concerns the effective crafting
skill at test time, through actual shade or temporary Epiphany, never any unrelated
gray skill. No global quality reconciliation, arithmetic DSL, Artha activation,
shade runtime or equipment stat generator is introduced.

The confirmed Weaponsmith audit (308/310) adds CreatedEquipmentQuality for ordinary
external weapon-quality categories, distinct from War Art's entry-specific quality
statements. Superior manufacture associates +2 crafting Ob and success with an
external superior-quality-weapon reference. Failed Weaponsmith manufacture links
to poor-quality-weapon output, with generic failure interaction unresolved rather
than replacement, stacking or exclusive-consequence semantics. Quality stats and
combat effects remain external; no deliberate-failure action or equipment generator
is introduced.

## D-026 — Training root usage, learning methods and source options

**Status:** Accepted — explicit user resolution and verified BWGR source audit

Training root purpose and learning methods are separate concepts. An explicit
Aptitude-only footnote sets rootUsage aptitude-only: the root is used only to
calculate Aptitude. Practice and instruction describe how learning tests are
earned, not additional uses of the root (Learning Training Skills, book 51 / PDF 53).
Do not infer root usage from a Training name or Skill Type. Missing root usage
remains untranscribed. The seven General footnotes are Antiphon Union Training
(255/257), Armor Training (256/258), Formation Fighting (274/276), Mounted Combat
Training (284/286), Shield Training (295/297), Skirmish Tactics (297/299), and
Two-Fisted Fighting Training (306/308).

Mounted Combat Training and Mounted Combat: Bowman Training are distinct source
identities/options, never display aliases or a fabricated Lancer Training identity.
Selection belongs to a specific source acquisition, subject to the source's
character/setting appropriateness, not globally exclusive ownership. Elven
Outrider grants the Bowman option; Elven Lancer grants ordinary Mounted Combat
Training (137/139). The Elven Lancer example owns both (130/132). Source mappings
are content, not stock-specific engine assumptions. Combat consequences stay
external subsystem references; no ownership, learning or combat evaluator follows.

## D-027 — Physical equipment identity and combat-use profiles are separate

**Status:** Accepted — explicit user resolution and verified Polearm source audit

Physical equipment identity is separate from combat-use profiles. A single physical
weapon may expose multiple combat/use profiles with different combat statistics
where the source establishes them; this is not a requirement for all weapons.
Selecting a profile for an attack does not create a separate inventory item.
Equipment-level state such as possession, loss, repair, quality, enchantment and
similar whole-item properties belongs to the physical item unless a source rule
explicitly targets a specific profile.

Fight/UI may render combat profiles as separate attacks or action rows while
retaining one underlying equipment identity. This is presentation, not two items.

Polearm is the first confirmed case: BWGR 289 / PDF 291 distinguishes blade cutting
from beak/blade-tip thrusting, with different damage and weapon length. Weapons
Appendix 554 / PDF 556 names Polearm Axe Strike and Polearm Thrust. Skill metadata
stores stable typed external profile references without duplicating numeric stats.
The profiles may remain unloaded; they are not dangling General skill identities.
No inventory runtime, profile generation, equipment modifications or Fight evaluator
is introduced by this decision.

## D-028 — Free-form narrative content and structured mechanical relationships

**Status:** Accepted — explicit user resolution and verified Rune Casting audit

Narrative content remains free-form while mechanical relationships to narrative
content are structured. Beliefs, Instincts and similar player-authored narrative
elements are not catalog entries and are not semantically interpreted by the
rules engine. Such entities should have stable runtime identity and may expose
machine-trackable metadata such as ownership, revision/version and status.
Rules may reference those entities and react to structural changes, while
judgments about meaning, thematic correspondence, fulfillment or appropriateness
remain manual/table adjudication unless RAW provides an objective procedure.

Rune Casting (BWGR 293 / PDF 295) is the first explicit motivating case. Its
integration distinguishes one target Belief from the caster character's commitment
Belief, preserves manual meaning/link judgments, and records missing/changed
commitment invalidation. A future runtime can bind those roles to concrete entity
identities and revisions without parsing narrative text. Fulfillment, fatal
fulfillment and target agency stay human decisions; their typed rewards are
metadata, not automatic character/campaign changes.

This decision adds no Belief catalog, predefined Belief types, semantic classifier,
text matching, narrative mutation/revision runtime, or Belief/Artha/fate/death/
campaign evaluator. It does not expand implementation to Instincts or Traits.

## Open decisions

The following require an audit or implementation spike before being accepted:

- final domain schema for Lifepath requirements and restrictions;
- representation of Leads and setting transitions;
- state-management approach beyond plain React/local domain state;
- persistence format and save/load versioning;
- exact strategy for importing the complete human lifepath/skill dataset;
- whether rule-reference metadata belongs directly on data records or in a separate mapping layer.
