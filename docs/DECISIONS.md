# Decisions

Durable project decisions live here. Rules-as-written belong in `RULES_NOTES.md`; this file is for implementation, architecture, interpretation and UX choices.

## D-001 — Clean-room Character Burner v2

**Status:** Accepted

The new application is implemented from scratch. The previous single-file HTML prototype is not migrated and is not a rules source. It may be consulted only as historical UX reference.

**Reason:** The prototype mixed rules logic, state and presentation, making localized fixes prone to regressions.

## D-002 — Rules logic is separate from UI

**Status:** Accepted

Rules evaluation and calculations must be framework-independent. React components consume rule results; they do not determine legality themselves.

## D-003 — Character Burner is data-driven

**Status:** Accepted

Lifepaths, settings, Leads, requirements, restrictions and point grants are represented declaratively wherever practical. Special cases should be explicit and testable rather than hidden in component conditionals.

## D-004 — Current temporary human scope is Peasant + Villager + City + Professional Soldier

**Status:** Accepted — temporary scope

The first playable human slice exposes **Born Peasant**, **Village Born** and **City Born** as initial choices.

The supported lifepath area for this slice includes the **Peasant Setting**, **Villager Setting**, **City Dweller Setting** and **Professional Soldier Subsetting**, including legal transitions among them where supported by Leads and requirements.

Professional Soldier is included as a supported reachable area; this is not a claim that it has its own Born lifepath. Likewise, this temporary scope is a product decision, not a claim that these are the only legal human Born lifepaths or settings in Burning Wheel.

This decision expires when the full human lifepath data audit is implemented.

## D-005 — Exact point accounting is an invariant

**Status:** Accepted

Every character-burning purchase records enough provenance to undo exactly what was spent. Reset/rollback must conserve point pools and must not infer refunds solely from the current exponent.

## D-006 — Skill adjustment UI uses +1 / -1

**Status:** Accepted

Opened skills display their exponent prominently and expose clear `+1` and `-1` controls. The rules layer remains responsible for determining whether either action is legal and what it costs/refunds.

## D-007 — Current web stack

**Status:** Accepted for v2 bootstrap

Use **TypeScript + React + Vite + Vitest** for the first implementation.

This is an engineering choice, not a Burning Wheel rule. Revisit only if the stack materially impedes rules accuracy, testing or maintainability.

## D-008 — Rulebook PDF stays outside Git

**Status:** Accepted

The legally obtained Burning Wheel reference PDF remains in the private ChatGPT Project used for rule research. The public repository stores concise paraphrases, source references and implementation data, not the PDF or large verbatim excerpts.

## D-009 — Rule explanations are part of the product

**Status:** Accepted

The simulator is a training tool, not merely a form. When practical, disabled or rejected actions should expose a reason generated by the rules layer and rendered as a clear explanation in the UI.

## D-010 — Interpretation policy for small RAW gaps

**Status:** Accepted

Burning Wheel sometimes relies on context and ordinary common sense instead of spelling out every implication as a separate prohibition or exception. When the rulebook does not state a minor implication literally, the project may adopt a narrow interpretation if the surrounding rules, terminology and fictional meaning make the intended behavior clear.

Such a conclusion must be labeled **project interpretation**, not RAW. The implementation and tests should encode the interpretation explicitly so it can be revised without pretending the book said something it did not say.

If two materially different readings remain plausible, or the choice would significantly change legal builds or outcomes, the question remains **OPEN** until explicitly resolved. “Common sense” is not permission to silently invent convenience rules.

## D-011 — A character has exactly one Born lifepath

**Status:** Accepted — project interpretation

A character has exactly one Born lifepath, and it is always lifepath index 0. No Born lifepath may become legal again later through a Lead, setting transition or repeated-lifepath logic.

The rulebook explicitly requires the first lifepath to be Born and describes that path as the character's birth/childhood and starting setting. The audited passage does not separately contain a universal sentence saying that a Born path can never be selected later, so this is recorded under D-010 as an explicit interpretation rather than overstated as a literal RAW sentence.

Recommended rules-engine rejection reason: `BORN_LIFEPATH_NOT_FIRST`.

## Open decisions

The following require an audit or implementation spike before being accepted:

- final domain schema for Lifepath requirements and restrictions;
- representation of Leads and setting transitions;
- timing of requirements whose wording refers to final/start-of-play state (for example Human Elder's starting-age condition);
- state-management approach beyond plain React/local domain state;
- persistence format and save/load versioning;
- exact strategy for importing the complete human lifepath/skill dataset;
- whether rule-reference metadata belongs directly on data records or in a separate mapping layer.
